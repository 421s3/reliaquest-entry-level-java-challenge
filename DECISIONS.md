# Decisions

## 1. Which endpoints did you add, and why does this system need them?

I added the terminate endpoint (POST/api/v1/employee/{uuid}/terminate). The system has contractTerminationDate, but no way to set it.
My endpoint allows the webhook to terminate the employee, but also doesn't delete their records entirely because it sets a state instead of removing the employee. Thus, the employee is terminate but their records remain within the employee management system. For behavior, repeat calls to termination return 200 with no changes to the original date because webhooks retry. For terminating someone who hasn't started, it returns 409 so that termination never happens before the hire date.

## 2. Did you add any dependency? What does it buy, and what does it cost?

Yes, I added the spring-boot-starter-validation dependency. By utilizing this dependency, I was able to handle automatic 400 responses, allow
declarative rules next to fields, and enable future scale for the project through ease of use for adding rules to new fields. Without the dependency I would have had to manually write validation checks. However, by adding this dependency the project now has one more thing that it has to maintain in order to function properly. Moreover, the dependency rules only cover single fields and the dependency's default error format required my error handler to become a clean response.

## 3. How did you handle errors and logging, and why those mechanisms?

For handling errors, I created GlobalExceptionHandler to map 404, 400 invalid UUID, validation, or malformed body, 409 invalid state for termination, and handled Spring's own 4xx exceptions so they wouldn't become 500s. This was easier for me to ensure that all errors had the same response shape and logged only once and only in one place. Moreover the class is annotated with @RestControllerAdvice which is what makes the class global in the first place. For logging, I used info on the state changes which were the create and terminate endpoints. I used warn on any of the client errors, and used error with stack trace for the 500 errors after my handler handled the exception. For malformed bodies, the handler logs only the exception type. All logs only include UUIDs and leave out personal information like names, salaries, emails, etc. 

## 4. Where the brief left a decision to you, what did you decide?

Required fields: I included all 8 of the fields, with only ContractTerminationDate being kept as optional. Should the consumer leave it null the program assumes they are currently employed. In addition to having the fields as a requirement, I included restrictions on the input to better match the fields. ContractTerminationDate, if input, must be after ContractHireDate, Age must be a positive number (used @Positive), and Salary must be a positive number. For age this is to ensure that there would be no 0s or negative values which could mean the data is missing or corrupt, and the same goes for salary. There is no upper limit for age since I felt that could cause some policy headaches (how old is too old to work?) and I would need more information to place a hard age cap. For the dates, this is so that an employee can't be terminated before they start which keeps records consistent and logical.

For fullName I only set that field by adding the firstName and lastName variables with a " " in between. This is so that if firstName or lastName is ever updated they refresh fullName. For UUID, this is randomly generated by the server. The Employee interface included both uuid and fullName, but my create body doesn't. Thus, the server generates the UUID and creates the full name from the previously mentioned string concatenation. Moreover, a separate DTO request keeps the information from being set in either field.

Error Status Codes: For choosing which status codes to use I went with 404 for unknown UUID as 404 is for can't find or doesn't exist exceptions. For an invalid UUID I used 400 for when the request is malformed. Lastly, I used 409 when the request is valid but the termination date is set before the employee has started working (hire date).  

Tests: I wrote the tests to create their own data to test on and assert the error messages to make sure that the exceptions were being handled properly, regardless of what the status code said (as there were multiple 400 errors that could mean several things if I only asserted the status codes).


## 5. What did you deliberately choose *not* to do?

One thing I deliberately chose not to do was create a DELETE for my endpoint to ensure that employee management records were still retained even after employee termination. I would revisit this if it becomes a necessity to fully remove employee records at the company after termination. I also considered creating a PATCH Endpoint for allowing the management system to update an employee's information. However, I decided not to commit to this endpoint because creating this would require a new data transfer object and because contractTerminationDate might be null it could never be changed through the endpoint because null is ambiguous. Moreover, I wanted to prioritize including termination. I would revisit this if after integrating SaaS needs to sync ordinary changes which would be necessary for information upkeep such as title updates and salary changes. 

For setting the termination date, the program checks if the employee is already terminated and then sets the date. There exists a scenario where if there are two concurrent calls they could both pass. For now, I think that this issue is harmless as both calls would store nearly the same time. I would revisit this problem with a synchronized method if concurrent terminations caused harm. Lastly, I decided to strictly use Instant.now() when implementing contractTerminationDate. This does mean that the system cannot schedule termination ahead of time besides doing it now. I would revisit this if there is a necessity for scheduled termination.
